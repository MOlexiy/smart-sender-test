# Smart Sender — тестове завдання (Senior Frontend)

Невеликий застосунок: вхід, список вебхуків і редагування. API повністю імітується через MSW за контрактом із завдання.

## Запуск

Потрібен Node.js 20+.

```bash
npm install
npm run dev        # http://localhost:5173
```

Інші команди:

```bash
npm test           # автоматизований тест (Vitest + MSW у Node)
npm run typecheck  # tsc -b (strict)
npm run lint       # oxlint
npm run build      # production-збірка (MSW працює і в ній — іншого бекенду немає)
```

## Стек

- **React 19 + TypeScript** (`strict`, а також `noUncheckedIndexedAccess`), збірка — **Vite**.
- **MSW 2** — мок API (у браузері через Service Worker, у тесті через `msw/node`).
- **TanStack Query** — серверний стан: кеш, стани завантаження/помилки, `keepPreviousData` для пагінації, інвалідація після редагування.
- **React Router 7** — маршрути й стан списку в URL.
- **React Hook Form** — форми й відображення серверних помилок біля полів.
- **Vitest** — тест.
- UI-бібліотеку не використовував: кілька простих компонентів і один CSS-файл, щоб не відволікати від логіки.

## Структура

```
src/
  api/                  # усе, що стосується HTTP — без React
    httpClient.ts       # транспорт: CSRF, rotate сесії, повтори запитів
    endpoints.ts        # функції під контракт (auth, me, webhooks)
    errors.ts, types.ts # ApiError, SessionExpiredError, типи контракту
    httpClient.test.ts  # тест паралельних 401 → один rotate
  session/              # локальна сесія: стан, вхід, вихід, захист маршрутів
  features/
    auth/               # сторінка входу
    webhooks/           # список, пошук, пагінація, редагування, query-хуки
  shared/               # fingerprint, queryClient, мапінг серверних помилок, дрібний UI
  mocks/                # MSW: стан «сервера» в пам'яті + обробники
```

Шари розділені так: **`api/`** нічого не знає про React, **`session/`** керує лише тим, чи залогінений користувач, **`features/`** — UI та query-хуки. Залежності йдуть в один бік: UI → query-хуки → api → httpClient.

## Ключові рішення

### Сесія і повтори запитів (`src/api/httpClient.ts`)

- Кожен запит має `X-Requested-With: XMLHttpRequest` та `credentials: 'include'` (сесію тримає мок — аналог HttpOnly-cookie, клієнт токенів сесії не бачить).
- **CSRF.** Перед першим API-запитом клієнт робить `GET /csrf` (single-flight: паралельні запити чекають один і той самий проміс). Токен передається в `X-CSRF-TOKEN` на POST/PUT. На **419** токен скидається, береться заново, а запит повторюється **не більше одного разу**.
- **401 → rotate.** Захищені запити (`/v1/*`) на 401 викликають `POST /auth/token/rotate` і повторюються один раз.
  - Кілька одночасних 401 чекають **один спільний** проміс rotate (`rotateRequest ??= …`).
  - Додатково є лічильник «епохи» сесії: якщо відповідь 401 прийшла на запит, відправлений *до* вже завершеного rotate, клієнт просто повторює запит без нового rotate.
  - Самі auth-запити (`login/issue/rotate/revoke`) позначені `protected: false`, тому rotate ніколи не запускає новий rotate.
  - Помилка rotate або повторний 401 → `SessionExpiredError` і подія `onSessionExpired`, на яку підписаний `SessionProvider`: він скасовує запити, очищає кеш TanStack Query і переводить у стан `anonymous` → редірект на `/login`.
- **Вхід.** `login → device_session_token → /auth/token/issue → /v1/me`. `device_session_token` живе лише в локальній змінній функції `signIn` — не в стані, не в localStorage і не в URL. Заголовок `X-Captcha-Token` передається заглушкою (віджет капчі не потрібен за умовою).
- **fingerprint** (`src/shared/fingerprint.ts`) — 32 hex-символи з `crypto.getRandomValues`, генерується один раз і зберігається в localStorage; передається в тілі auth-запитів.
- **Вихід.** `/auth/token/revoke`, далі — у `finally` — очищення локального стану й кешу (навіть якщо revoke впав, локально користувач розлогінюється).
- **Перезавантаження сторінки.** На старті застосунок пробує `GET /v1/me` (з реальним cookie сесія відновилася б). Мок живе в пам'яті, тож після перезавантаження буде 401 → rotate 400 → екран входу. Поточна адреса зберігається в `state` редіректу, і після входу користувач повертається на ту саму сторінку з тими самими `page`/`search`.

### Список вебхуків

- Сторінка й пошук — у URL (`/webhooks?page=2&search=order`), хук `useWebhookListParams`. Значення за замовчуванням з URL прибираються. Тому працюють перезавантаження та «назад»/«вперед».
- Зміна пошуку завжди скидає сторінку на першу.
- Поле пошуку з debounce (350 мс); при навігації «назад»/«вперед» поле синхронізується з URL.
- Стани: завантаження, «Оновлення…» при переході між сторінками (стара сторінка лишається на екрані завдяки `keepPreviousData`), порожній результат, помилка з кнопкою «Retry».
- Якщо в URL сторінка більша за останню (стара закладка), відбувається `replace` на останню наявну.

### Редагування

- Окрема сторінка `/webhooks/:id` (а не модалка) — на неї можна дати посилання, і вона коректно працює з «назад».
- Посилання «Edit» передає поточні параметри списку, тож «Назад»/«Cancel»/успішне збереження повертають на ту саму сторінку пошуку.
- Валідація навмисно лише серверна — правила визначає контракт. Помилки 422 з `payload` розкладаються біля відповідних полів (`applyServerErrors`); помилки без поля показуються над формою.
- Після збереження оновлюється кеш деталі й інвалідуються списки.
- Окремий стан для 404.

### Мок (`src/mocks/`)

Реалізований за правилами з завдання: один користувач, 28 вебхуків, стан у пам'яті; сесія 30 с, rotate продовжує на 30 с; до `issue` і після `revoke` rotate повертає 400; CSRF-токен фіксований і перевіряється на POST/PUT **до** виконання операції (419); `/auth/login` вимагає непорожній `X-Captcha-Token`; пошук — підрядок без урахування регістру; помилки у форматі `{ error: { type, message, payload } }`.

## Тест

`src/api/httpClient.test.ts` (Vitest + `msw/node`, той самий набір обробників, що й у браузері):

1. **Основний (вимога завдання):** вхід → примусове завершення сесії в моку → два паралельні запити (`/v1/me` і `/v1/webhooks`) отримують 401 → рівно **один** `rotate` → обидва повтори успішні.
2. Помилка rotate → обидва запити отримують `SessionExpiredError`, подія завершення сесії викликається один раз.
3. 419 → повторне отримання CSRF-токена й успішний повтор.

## Що не зроблено / можна покращити

- Перемикання активності вебхука (`active`) — у контракті `PUT` приймає лише `name` і `url`, тому активність лише відображається.
- Клієнтську валідацію не додавав свідомо (див. вище); у реальному продукті поставив би zod-схему, спільну з серверними правилами, для швидкого фідбеку.
- Компонентних/E2E-тестів немає — за умовою потрібен один тест; основні сценарії перевірив вручну в браузері.
- i18n: тексти інтерфейсу англійською, без бібліотеки перекладів.
